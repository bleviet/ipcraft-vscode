# Block design containers: link a black box to its Tcl (design draft)

Status: approved 2026-11-11 (expand inline, one link per block design name,
`.ipcraft/bd-links.json`). Implementation plan:
`docs/superpowers/plans/2026-11-11-block-design-container-links.md`.

## Problem

`fpga/dfx_tandem_xilink_vek385/src/tcl/top.tcl` instantiates seven block design
containers (Vivado "block design containers", BDC):

```tcl
set base_partition [ create_bd_cell -type container -reference base_partition base_partition ]
set_property -dict [list CONFIG.ACTIVE_SYNTH_BD {base_partition.bd} \
                         CONFIG.LIST_SYNTH_BD {base_partition.bd} ...] $base_partition
```

`bdTclCommands.ts` `createCell` accepts only `-type ip|hier|module`. A container
cell is dropped with "Unknown cell type", and `bdTclGraphBuilder.ts`
`addReferencedBlackBoxes` then shows it as a `blackbox` with only the pins that
nets happen to touch. The user cannot see what is inside, and cannot tell
ipcraft where the child design is.

The containers in vek385 are `datamover_stimulus`, `ethercat_quad_port`,
`base_partition`, `rm_aie_test`, `rm_fmc_tq_breakout` (DFX list
`rm_fmc_samtec_firefly.bd:rm_fmc_tq_breakout.bd`), `rm_fmc_gtyp_samtec_firefly`
and `mda_partition`.

## Why a file-name match alone is not enough

`base_partition.tcl` exists twice, in `fpga/dfx_tandem_xilink_vek280/src/tcl/`
and in `fpga/dfx_tandem_xilinx_common/src/tcl/`; both declare
`set design_name base_partition`. Only the second is used by vek385. The
authoritative mapping is the `DESIGN` list of `add_vivado_project` in
`fpga/dfx_tandem_xilink_vek385/CMakeLists.txt`, which lists `top.tcl` together
with `../dfx_tandem_xilinx_common/src/tcl/base_partition.tcl` and the other BD
Tcl files of the same project.

## The `.bd` is a build product, not a source

`base_partition.bd` in `CONFIG.LIST_SYNTH_BD` does not exist in the source
tree. Vivado writes it when the build sources the BD Tcl: the Tcl's
`set design_name base_partition` (the `write_bd_tcl` header) runs
`create_bd_design $design_name`, which creates
`<project>.srcs/sources_1/bd/base_partition/base_partition.bd`. In this repo
`.bd`, `*.gen/`, `*.srcs/`, `*.runs/` and `build*/` are disposable output
(see the superrepo AGENTS.md). So the design treats the `.bd` name only as a
key:

- The container's `.bd` name is matched against the `design_name` of the
  **generator** Tcl, which is the source of truth. ipcraft never reads or
  links a `.bd` file, and never offers one as a candidate (not even in
  Browse; the dialog filters for `*.tcl`).
- A generated `.bd` may be missing, stale or from another board's build. Its
  presence or absence plays no part in resolution.
- Build trees can hold Tcl that *looks* like a generator, e.g.
  `*.gen/.../hw_handoff/<bd>_bd.tcl` or a `write_bd_tcl` export, with the
  same `design_name`. The candidate index skips the directories in
  `workspaceFilter.ts` (`*.gen`, `*.runs`, `*.sim`, ...) and the user's
  `search.exclude`; a Tcl listed in the design's CMake project (rank 1) wins
  over any copy elsewhere.
- `design_name` must equal the name exactly. A prefix does not count:
  `base_partition_sim_top.tcl` declares `base_partition_sim_top`, so it is not
  a candidate for `base_partition`.
- `CONFIG.LIST_SIM_BD` and `ACTIVE_SIM_BD` may name a different, simulation-only
  BD. The viewer follows the synthesis BD (`ACTIVE_SYNTH_BD`); the simulation
  BD stays visible in the Parameters list.

## Approaches considered

1. **Manual mapping in `.ipcraft/` only** (the original proposal). Simple, but
   every user must assign seven files by hand per design, and the stored path
   silently goes stale when files move.
2. **Annotation comment in `top.tcl`** (`# ipcraft: base_partition -> ...`).
   Travels with the design, but `top.tcl` is regenerated by `write_bd_tcl`
   and merged with `merge_bd_tcl_export.py`; the comment can be lost and it
   pollutes a vendor-format file.
3. **Recommended: parse containers, resolve automatically from ranked
   evidence, and let the user override; store only overrides in `.ipcraft/`.**
   In the vek385 case all seven containers resolve with no user action; the
   `.ipcraft` file is needed only for ambiguous or unusual layouts.

## Design (approach 3)

### 1. Parser: a real `container` cell

- `createCell` accepts `-type container -reference <bd>`. New instance kind
  `container` in `SystemInstance.kind`, carrying
  `container: { reference, activeBd, alternatives: string[] }` read from
  `CONFIG.ACTIVE_SYNTH_BD` and `CONFIG.LIST_SYNTH_BD` (colon separated, `.bd`
  stripped). `activeBd` falls back to `reference`.
- Its pins come from the nets as today (no behavior loss before resolution).
- No more "Unknown cell type" warning for containers.

### 2. Candidate resolution (pure function, `resolveBdContainers.ts`)

Input: the container, the design file path, a list of `BdTclEntry`
(`{ file, displayName, uri, designName }`, `designName` from
`set design_name X`, read with a cheap regex like `fileEntries.ts`), the
CMake project lists, and the stored overrides. Output: the chosen entry, the
ranked candidates, and a diagnostic. Evidence, strongest first:

| Rank | Evidence |
|---|---|
| 0 | Override in `.ipcraft/bd-links.json` for this design file and instance |
| 1 | A `CMakeLists.txt` whose `add_vivado_project(... DESIGN ...)` list contains the design file also lists a Tcl whose `design_name` equals `activeBd` |
| 2 | Any workspace `.tcl` whose `design_name` equals `activeBd` |
| 3 | A file named `<activeBd>.tcl` |

Within one rank the nearest file by `treeDistance` wins (as in
`matchDefinitions.ts`). Two candidates at the same rank and distance are a
warning ("ambiguous, assign one") and the instance stays a container. No
candidate: an info diagnostic with the hint to assign a Tcl.

The CMake parse reads only the `DESIGN` argument of `add_vivado_project`,
resolving paths relative to the `CMakeLists.txt`; anything it cannot read is
ignored (rank 1 just does not apply).

### 3. Expansion: reuse the subsystem graft

`expandSubsystems.ts` gets a BD Tcl branch next to the qsys one: read the
chosen file with `BdTclReader`, recurse (self-instantiation guard as today),
and graft it with `graftSubsystem`. The container becomes a hierarchy level,
its pins come from the child design's ports, and the details panel shows the
source file with an "Open Tcl" link. For a DFX list the active RM is
expanded; the details panel lists the alternatives.

`EnrichmentIo` gains `listBdTclFiles()` and `listCmakeProjects()`; the VS Code
adapter indexes `**/*.tcl` and `**/CMakeLists.txt` with `WorkspaceFileIndex`
(same pattern as `SubsystemExpander`), the CLI adapter walks the tree.
`ipcraft render` therefore gets the same result.

### 4. User override

- Context-menu and details-panel action on a container or black box:
  "Assign Tcl...". A QuickPick shows the ranked candidates with their evidence
  ("listed in fpga/.../CMakeLists.txt", "design_name matches", "file name
  matches"), then "Browse...", then "Remove assignment".
- Stored in `<workspace>/.ipcraft/bd-links.json`, committed with the repo,
  paths relative to the workspace folder:

```json
{
  "version": 1,
  "links": {
    "fpga/dfx_tandem_xilink_vek385/src/tcl/top.tcl": {
      "base_partition": "fpga/dfx_tandem_xilinx_common/src/tcl/base_partition.tcl"
    }
  }
}
```

  Key is the design file and the container's `reference` (the BD name), so one
  assignment covers every instance of the same BD. A link to a missing file
  is a warning and resolution falls back to ranks 1-3.
- The file is watched; editing it refreshes the open viewer.
- The workspace walk already skips `.ipcraft/`.

### 5. Error handling

All failures are diagnostics on the container's line, never a failed render:
unreadable Tcl, self-instantiation, ambiguous candidates, stale override,
child design without the ports the parent nets use (those pins are still
drawn, flagged unconnected-in-child).

### 6. Tests

- Parser: container cell with single and DFX lists; no unknown-type warning.
- Resolver: each rank, rank precedence, tie by distance, ambiguity, stale
  override; the vek280/common `base_partition.tcl` case resolves to common via
  CMake; a `hw_handoff` Tcl under `*.gen` with the same `design_name` is
  not a candidate; a present or absent `.bd` changes nothing;
  `base_partition_sim_top` is not a candidate for `base_partition`.
- Expansion: graft of a small BD Tcl child, recursion guard.
- Overrides store: read, write, remove, invalid JSON.
- A fixture modelled on vek385 (`top.tcl` + `CMakeLists.txt` + two
  `base_partition.tcl`) rendered end to end through the CLI path.
- Docs: `docs/how-to/view-a-system-design.md` gains "Link a block design
  container to its Tcl".

## Out of scope

- Switching the shown DFX reconfigurable module from the UI (only listed).
- Writing anything back into `top.tcl` or `CMakeLists.txt`.
- `.bd` (JSON) files as sources: they are build products (see above); only the
  generator BD Tcl is linked.

## Decisions

1. A linked container is expanded inline (grafted as a hierarchy level).
2. A link applies to every container of one design file that shows the same
   block design name (the active synthesis BD).
3. Links are stored in `<workspace folder>/.ipcraft/bd-links.json`.

Refinements made while planning:

- An unresolved container keeps `kind: 'blackbox'` (already drawn everywhere)
  plus a new `container` field; a resolved one becomes `hier` through
  `graftSubsystem`. No new instance kind.
- Build trees are skipped with the viewer's existing ignore list (`*.gen`,
  which holds `hw_handoff` Tcl, `*.runs`, `*.sim`, ...) and the user's
  `search.exclude`. No extra `*.srcs` or `CMakeCache.txt` rule: `*.srcs`
  holds `.bd`, not Tcl, and the CMake evidence (rank 1) wins over any copy.
- The simulation BD and the alternatives are visible in the Parameters list;
  the details panel adds only the active BD, the alternatives and the source.
