# Contributing to IPCraft

Thanks for considering a contribution. This file covers what you need to get
a change through CI and review. For architecture and module-level
conventions, read [CLAUDE.md](CLAUDE.md) first — it is the canonical map of
the codebase and is binding for any change.

## Setup

Requires Node.js 20+, npm, and VS Code 1.80+.

`ipcraft-spec` (bus definitions and JSON schemas) is a **git submodule**.
Clone with `--recurse-submodules`, or if you already cloned without it:

```bash
git submodule update --init --recursive
```

`npm run pretest` runs `scripts/check-submodule.js` and fails if the
submodule is missing, so this step is not optional.

```bash
npm install
npm run generate-types   # regenerate src/domain/*.types.ts from ipcraft-spec schemas
npm run compile
```

Press **F5** in VS Code to launch an Extension Development Host.
See [docs/getting-started/development.md](docs/getting-started/development.md)
for the full setup reference, including the optional CMake target wrapper.

## Generated files — do not hand-edit

- `src/domain/*.types.ts` and `src/generator/contract/templateContext.types.ts`
  are regenerated by `npm run generate-types` from
  `ipcraft-spec/schemas/*.schema.json`. Edit the schema, not the generated
  type file.
- `dist/` is a build output (webpack + `CopyWebpackPlugin`). Templates live in
  `src/generator/templates/` — edit them there, never in `dist/templates/`.
- `src/webview/types/ipCore.d.ts` and `memoryMap.d.ts` are an older type layer
  the generator script does not touch; when a schema field changes, update
  these by hand alongside `src/domain/*.types.ts`.

## Formatting, lint, type-check

```bash
npm run format        # Prettier, src/**/*.{ts,tsx}
npm run lint          # ESLint — zero warnings allowed
npm run lint:fix       # auto-fix what can be fixed
npm run type-check    # tsc --noEmit
```

`npm run lint` must pass with zero warnings before any commit — the
pre-commit hook (husky + lint-staged) enforces this locally, and CI enforces
it again.

## Tests

Use the smallest suite that covers your change, then run the broader checks
before opening a PR. Full guide: [docs/testing.md](docs/testing.md).

```bash
npm run test               # unit tests (Jest, jsdom) — alias of test:unit
npm run test:browser       # Playwright browser tests (Chromium headless)
npm run test:e2e           # VS Code integration tests (@vscode/test-electron); run npm run compile first
npm run test:integration:hdl     # HDL generation + GHDL/iverilog compile gate
npm run test:integration:vivado
npm run test:integration:quartus
```

Jest, Playwright, and webpack configs live under `config/`, not the repo
root, so pass `--config` explicitly when running a single file or test:

```bash
npx jest --config config/jest.config.js src/test/suite/services/YamlValidator.test.ts
npx jest --config config/jest.config.js -t "should parse valid YAML"
```

Expectations by change type:

| Change | Add/update tests in |
|---|---|
| Pure algorithm, parser, or service | `src/test/suite/algorithms/`, `src/test/suite/services/` |
| Hook or React component | `src/test/suite/hooks/`, `src/test/suite/components/`, run `npm run test:browser` |
| Extension host / VS Code command | run `npm run compile` and `npm run test:e2e` |
| Generator template or HDL/vendor output | `npm run test:integration:hdl` plus the relevant vendor suite |
| Bug fix | add a regression test reproducing the bug |

## Local validation checklist

Run before opening a pull request:

```bash
npm run lint
npm run type-check
npm run test:unit
npm run compile
```

If your change affects extension-host behavior, also run `npm run test:e2e`;
if it touches editor UI, also run `npm run test:browser`.

## Workflow

1. Create a branch from `main`.
2. Make focused changes — see the module-size and single-responsibility
   guidance in [CLAUDE.md](CLAUDE.md).
3. Add or update tests.
4. Run the validation checklist above.
5. Open a PR using the pull request template; it mirrors this checklist.

Commit messages use conventional prefixes (`feat:`, `fix:`, `docs:`, `test:`,
`refactor:`, `chore:`). Full contributor guidelines, including commit-message
examples and code-style notes, are in
[docs/contributing/guidelines.md](docs/contributing/guidelines.md).

## Getting help or reporting issues

See [SUPPORT.md](SUPPORT.md) to route usage questions, bug reports, and
feature requests correctly, and [SECURITY.md](SECURITY.md) for vulnerability
reports — never file those as a public issue.
